# 0016 — Official order numbers come from a PostgreSQL sequence

- Status: accepted
- Date: 2026-11-18

## Context

A draft carries a draft number; submitting it gives the order its official number, `FR` followed
by six digits, which then names the order everywhere — in the URL, in search, on the invoice.
The number must be unique, must not be reused, and two drafts submitted at the same moment must
not get the same one. Until submitting existed, only the seeder wrote official numbers.

## Decision

A sequence, `order_number_seq`, is the only source of official numbers. The application asks a
port, `IOrderNumbers.NextAsync`, which Infrastructure answers with `nextval`. The handler asks the
order whether it can be submitted before it takes a number, so a refused submit takes none.

The migration that creates the sequence starts it after the highest official number already
stored. The seeder sets it to the highest seeded number once a rebuild of the sample data is
committed, so the first submit after every rebuild gets the same number.

The unique index on the number of every order that is not a draft stays: the sequence makes a
duplicate impossible in normal work, the index makes it impossible altogether.

## Alternatives

- **`MAX(number) + 1` in the handler** — two concurrent submits read the same maximum; the unique
  index would refuse one of them, turning a normal case into a retry. It also scans or sorts on
  every submit.
- **A counter row updated in the submit's transaction** — dense numbers, no gaps. Every submit of
  the company then waits on one row lock, and the number is tied to a transaction that may still
  fail. Nothing in the domain asks for dense numbers.
- **The number generated by the domain** — the aggregate cannot know what other orders hold; it
  is given the number and owns the rule of when it may take it.
- **A sequence per company** — the right shape with many tenants and a prefix of their own. One
  company exists; the port hides the choice.

## Consequences

- Numbers are unique and increasing, not dense: a submit that loses an optimistic-concurrency race
  after `nextval` leaves a gap. `nextval` is never rolled back, by design.
- `setval` is not transactional either. It runs after the rebuild commits, so a failure can only
  leave the sequence too high — a gap — never low enough to collide.
- The sequence is database state outside the tables: a restore or a copy of the data must carry
  it, and the rebuild resets it explicitly.
- With a second instance, a `nextval` during another instance's rebuild is not isolated from it.
  The demo runs one instance ([ADR 0015](0015-the-demo-rebuilds-its-sample-data.md)).
