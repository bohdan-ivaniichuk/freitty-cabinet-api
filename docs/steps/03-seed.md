# 03 — Seed

> **Draft, not groomed.** Written ahead of the grooming session so it does not start from zero.
> Everything under *Decisions* is a proposal; *Open questions* is what the session has to settle.
> Nothing here is input for implementation yet.

## Goal

The database is filled with sample data taken from the mockup and normalised as
[`mockup-analysis.md`](../../assignment/mockup-analysis.md) asks, so every screen has something
true to show. The data is built through the `Order` aggregate of [step 2](02-domain.md), at
startup, once.

## Decisions

- **Through the aggregate.** Every order is built with the methods of `Order`; a refusal stops the
  startup. Sample data therefore cannot contradict a domain rule, and the seed is the first real
  consumer of the whole lifecycle.
- **At startup, after the migration, only into an empty database** (no company row). One
  transaction: either all of it or nothing. Runs in the deployed app too — the demo needs data.
- **Dates are relative to the day of seeding.** The mockup's "today" (17 Apr 2026) maps to the
  current day in the hub's time zone; every other instant keeps its distance from it. With literal
  dates "Completed (30 d)", the chart and the "Last 30 days" filter would be empty.
- **`TimeProvider` is registered here** (`TimeProvider.System`) — the seed is its first consumer.
  Tests replace it with `FakeTimeProvider`.
- **Two kinds of data.** *Hero orders* are the seven orders the mockup draws, written by hand so
  they match the screens. *History* is a deterministic set of completed orders spread over the last
  twelve weeks, so the KPIs, the chart and pagination have enough rows. No randomness: the same
  seed on the same day gives the same database.
- **Money is realistic**, not `$1`: supply prices from a small price list, an invoice amount
  computed as the supply subtotal plus billable units times a rate constant of the seed. The
  model has no rates; the constant lives in the seed and is said so in the presentation.
- **A switch for tests.** Integration tests share one database and must not find seed rows in it.
  `Seed:Enabled` is `true` in `appsettings.json`; `ApiFactory` turns it off; the seed tests run on
  their own database with it on.

### History

About forty completed orders over the last twelve weeks, generated by a loop from fixed tables
(type, hub, cargo, carrier, creator), each with a paid invoice. Numbers below the hero range.
Enough to give a non-flat chart and three pages of the list.

### Startup

`Program.cs`: migrate → seed (when enabled and the database is empty) → listen.

## Acceptance criteria

- [ ] `docker compose down -v && docker compose up -d --build --wait` gives a database with the
      seven hero orders and the history; a restart adds nothing.
- [ ] Each hero order, read back, has the status, quantities, alerts and transport of the table
      above.
- [ ] No order number, Ref N or amount in the database contradicts another (the inconsistencies
      listed in `mockup-analysis.md` are gone).
- [ ] `dotnet test` is green; no test outside the seed tests sees seed rows.

## Tests

- Seeding an empty database creates the reference data, the hero orders and the history —
  integration
- Each hero order is in the state the table describes — integration
- A second start does not seed again — integration
- With the clock fixed, the completed orders of the last 30 days and the scheduled dates fall where
  expected — integration
- The API starts with seeding switched off and an empty database — integration

## Out of scope

- Endpoints that read the data — steps 4–6.
- A way to reset or reseed other than dropping the volume.

## Open questions

1. Seed in the deployed app unconditionally, or behind a setting that the deploy turns on?
2. Which day is "today" for an instant in the mockup: the calendar day in the hub's zone at startup?
   And does a database seeded last week look stale on the day of the presentation — is a reseed
   needed before the demo?
3. How much history: forty orders over twelve weeks, or enough to make the query plans of step 4
   meaningful (thousands)? A larger, separate data set only for `EXPLAIN` may be the better answer.
4. The mockup's counters (Active 7, Completed 24, All 27, Alerts 2) cannot all hold at once. Which
   of them should the seed aim for, if any?
5. FR001681 is two days late in the mockup and DRAFT-003 is dated yesterday. Keep the dates as
   drawn or move both into the future, as proposed?
6. FR001383 with a partial Loading (6 of 11) changes one row of the operations table. Accept, or
   keep the row and drop the "On Stock" badge?
7. Invented values — destinations for FR001383 and FR001668, the Cross-Dock kind of FR001383, the
   company balance, prices and the billing rate. Who picks them?
8. Is the current user ("User 1") a seeded row that step 4 looks up by a setting?
